# Bot execution and simulation boundaries

Read this to distinguish active vassal execution from retained population machinery. See the [project map](README.md), [vassal duties](vassals.md), [world/combat](world-combat.md) and [AI conversations](ai-social.md).

## Current activation is enforced in code

`src/GameServer/Bot/Population/PopulationConfig.js` applies `ownedOnly=true` after file/environment overrides. This is stronger than disabled defaults in `config/default.ini`.

| Active owned-only path | Retained path not started by this policy |
| --- | --- |
| Registered vassal restore and live BotAI | Ambient population generation/seeders |
| Vassal gathering, party play and physical supply trips | Cold resolver and background parties |
| Lifecycle persistence and 30-second owned-actor snapshots | Director, phase policy, background governor/jobs and legacy repair jobs |
| Configured WAL maintenance | Autonomous clan founding/planning/simulation |
| Native movement and pathfinding workers | Legacy cold market/crafting/population scheduling |

`ClanSimulationConfig.js` additionally forces autonomous clan simulation off. `src/NodeL2.js` skips its planner and gates the legacy hot-load hook. Old INI overrides, historical rows or the presence of a module do not reactivate those services.

## Settings boundary

WorldObserver Bot settings describes **player-owned vassal behavior and optional AI dialogue**. Owned-only is read-only. `pvpAggression` (0..1) and `knowledgeErrorsEnabled` remain restart settings because `PopulationConfig` snapshots file/environment overrides; knowledge is not erased. PvP is initiation/risk/retreat behavior, not a probability of attacking every encounter, and self-defense remains at zero. Population environment ownership locks the relevant controls.

`useBssdOutOfCombat` is a restart setting, disabled by default: bots do not automatically charge blessed spiritshots for peaceful buffs/heals/other magic. Offensive casts (including the opening cast), the bot's own combat state and active party combat still permit charging; merely selecting a hostile leader target is not combat. WorldObserver renders **Use BSSD outside combat** as a checkbox; `BOT_USE_BSSD_OUT_OF_COMBAT` can own the setting. Player auto-shot preferences, ordinary spiritshots and soulshots are unchanged.

Inactive ambient counts/seeders, cold travel, background services, autonomous clans and static-shot restrictions are not offered as functional controls. Diagnostics remain restart settings under Server management with master/detail dependency. AI enabled/model/router/concurrency have a separate live dispatch contract; see [AI](ai-social.md) and [Settings](world-observer.md). Saving a configuration never starts workers or restarts gameplay.

## Live bot lifecycle

- `src/GameServer/Bot/BotManager.js::init` initializes vassal/lifecycle services and restores `fetchOwnedVassalCharacters()` rather than an ambient roster.
- `restoreOwnedVassal` validates registry membership and coalesces concurrent restoration; spawn admission also checks the owned character identity.
- `src/GameServer/Bot/Population/BotLifeState.js` loads owned lifecycle rows without legacy cold recovery.
- `src/GameServer/Bot/BotSession.js` adapts the native actor/session interface; live bots still use actor movement, skills, effects, inventory and combat.
- `src/GameServer/Bot/BotAI.js` owns per-session scheduling, wakeups and tick dispatch. `Bot/AI/States/` contains narrower hunting/following/resting/service state handlers.
- `src/GameServer/Bot/AI/VassalOrders.js` takes responsibility for non-companion owned duties and their continuation fences.
- `Population/Cooldown.js` refuses registered vassals. Owned actors do not become cold merely because the nearest human leaves.

Rule-based execution is distinct from LLM dialogue. It is not globally reproducible simulation: native timers, current time and randomized choices still affect behavior.

## Scheduling and level of detail

`BotAI.scheduleTick/wakeup` schedule actor work; state handlers are not independent uncoordinated game loops. Busy operations and explicit continuations must retain their identity checks before releasing holds or publishing results.

`HotAiDispatcher` enters asynchronously and runs urgent-first FIFO batches capped at 16 tasks or a soft 2-ms synchronous budget, checking time between tasks and while skipping stale/canceled entries. One timer continues remaining work; in-tick wakeups coalesce without adding redundant drains. A real-player timer may run after several actors, not necessarily after each actor. Individual tasks and Promise continuations are not preempted. Cancellation, urgent promotion and BotAI generation/next-tick ownership fences remain in force; task/error-handler failures must not strand the queue. Queue heads replace per-task front removal, with threshold-based amortized compaction so consumed entries cannot accumulate behind a steady backlog. Under developer diagnostics, `batches` counts drain turns and `yields` counts batch continuations; per-task samples and cumulative counters retain the [observer diagnostic definitions](world-observer.md#runtime-performance-diagnostics).

`Bot/AI/HotActorLodPolicy.js` distinguishes full, visible and preload detail for hot actors. These labels describe live scheduling/detail, **not cold ownership**. Vassals promote to full owned context even without nearby players, and non-companion duty scheduling bypasses ordinary low-detail delays.

`PartyCompanionService.attach/attachRoster` starts initial assembly in place rather than teleporting admitted bots. `States/FollowingState.tickTravel` uses `CompanionNavigationRecovery` and the native bounded worker pathfinding to walk into the leader's 250-unit follow range, retaining active routes and replanning when the leader moves substantially. During that approach, normal distance-based catch-up and stuck-recovery teleports run before the joining walk, while intertown gatekeeper transit stays disabled. After the existing bounded navigation retries are exhausted, the bot reports the failed path in party chat using ten short variants; `BotPartyChat` deduplicates this report per bot for 60 seconds and applies its shared coordination cooldown. Queue/capacity deferrals alone do not produce a no-path report. Combat/control/karma restrictions remain in force. Arrival or detachment clears the live assembly marker; subsequent follow/recovery behavior is unchanged.

Post-party safe rest measures eligible live time, not elapsed server downtime. See [vassal lifecycle](vassals.md) for the ten-minute rest and recovery rules.

## Full and map status reads

`Bot/AI/BotStatus.js` owns both read shapes. `getStatus` retains detailed party/nearby, movement, gear, effects, trade, inference and persona output; `BotAI.getStatus` also updates the full `session.botStatus` cache. Native panels, snapshots and gameplay status consumers keep this contract.

`BotStatus.getMapStatus` returns internal projection input only: identity/class/level, mode/intent/role, home/location, compact party core and the dead blocker. `BotAI.getMapStatus` forwards without writing that cache; `BotManager.getAllBotMapStatuses` preserves the full enumeration's actor filtering and order. Observer map/directory initialization and refresh use this API; full snapshot, clan/native and detail readers retain the full contract.

The lean read is not pure: it retains ambient TTL refresh/journaling, settings/pull/combat/threat inspection, effect pruning, trade/negotiation expiry, inference-budget pruning and policy restore in the full reader's relative order. Party inspection can synchronize raids and update player auto-fight constraints. Internal party/world scans and some summary allocations remain necessary through existing entrypoints; this is not a claim of globally linear map work or measured CPU savings.

Lifecycle capture, equipment shopping and dialogue infer a live actor's current role through `BotRoles.inferRole`, not observer-driven cache freshness. Capture reuses that role for both stats and build hints. Dialogue preserves stronger explicit role overrides and its existing actorless fallbacks.

## Native class decisions

- `Bot/AI/BotClassPolicy.js` derives class/ancestry skill eligibility, role, PvE/PvP solo/party context and resource preferences.
- Actual learned skills take precedence over theoretical availability. Policy coverage does not imply every actor has trained every skill.
- `Bot/AI/BotCombatUtility.js` applies validity/resource gates before preference scoring. Native attack/cast checks still decide whether an action executes.
- Action feedback distinguishes accepted requests from actual effect results; an accepted but interrupted cast need not have produced its effect.
- `Bot/AI/BotDecisionService.js` provides a narrower recovery/follow/target/spot recommendation path; it is not the universal scheduler.
- `Population/ColdClassPolicy.js` adapts retained cold profiles to shared selection without reproducing native geometry or timing.

Party damage mages use `Bot/AI/PartyMageRecovery.js` before ordinary state and raid routing: when MP cannot pay for any learned, allowed offensive attack (or reaches zero), a safe mage sits until 30% MP, then resumes spending without a damage-skill reserve. Reuse alone does not start recovery. A party's ongoing fight does not interrupt that cycle; direct NPC pressure yields to defense, and PvP defense retains its earlier priority. Explicit rest and HP recovery remain separate. Other roles and solo MP recovery keep their existing thresholds.

During raid combat, `Bot/AI/PartyRaidCombat.js::combatRaidBuffs` refreshes ordinary party buffs as well as songs/dances through `BotSupportPlanner`, using its existing expiry thresholds and cast reservations. Only currently reachable actions compete for selection: an outlying member cannot block nearby rebuffs or pull a buffer through the encounter. Buffs may interrupt a provider's auto-attack, not an active cast or movement; healing, resurrection and tank duties retain their earlier priority. The bounded minimal rebuff after resurrection remains separate.

While a connected leader's auto-fight run is active, `Actor/PlayerAutoFightPolicy.js` adds temporary zone/recovery constraints to companion designated pulls, the tank fallback and native offensive recipient expansion. Recovery suppresses routine buffs/charge preparation and non-emergency Recharge without rewriting pull settings or detached vassal duties. Inspection is not an assist target. See [auto-fight ownership and limits](world-combat.md#connected-player-auto-fight); ordinary behavior resumes outside the run.

`BotClassPolicy.skillAllowed` adds an optional pre-selection filter; ordinary bots without a player controller retain their learned-skill policy. Offensive/charge choices, `BotSkillCapabilities`, `SummonerTactics` and support caches apply that filter. `BotHealingPolicy` shares the narrow healing-priority decision with `FollowingState`, not its movement/service state machine. An eligible automated leader joins the existing support-provider set and executes only its own native casts; no player BotAI session, direct service buffs or player loadout cleanup is introduced.

New player/companion targets under that run also pause while `PartyPulling.hasDeadPartyMember` detects a fallen party member or `partyRevivalAttempt` is pending; already engaged combat and defensive actions remain legal. Companion Sweeper is corpse collection, not offensive initiation: it retains native corpse, spoil ownership, range and resource checks without applying the live-monster acquisition predicate. Other corpse-targeted offensive skills are not exempt.

The source-adjacent [class policy](../src/GameServer/Bot/AI/CLASS_POLICY.md) describes consumers and approximations. Engineering preference scores are not historical C4 facts, optimal rotations or gameplay certification.

## NPC escape and defensive reassessment

- `PartyAwareness.npcsTargetingActor` projects live, nearby NPCs currently targeting the actor. Escape continuation uses that state, not time since damage or residual hate; an NPC returning home is no longer a pursuer.
- `States/FleeingState.js` stops an obsolete escape route when pursuit ends. While a solo bot is pursued, it reassesses combat at most once per second using `BotThreatAssessment.js`: current HP/MP, learned attacks, an already present summon, target resistance/remaining HP and the combined pressure of up to six attackers. Unknown combat stats or a larger group do not justify re-engagement. A recovering bot also passes the existing encounter-readiness gate; protected raids and unsafe hunting grounds are not resumed this way.
- Hunting/resting self-defense uses the same assessment. The existing emergency-finisher policy may still justify a safe last hit instead of retreat. These are conservative estimates, not predictions of guaranteed combat outcomes.
- `fleeStart` measures the whole escape episode. The 30-second limit replaces a stale movement leg; it neither resets the episode nor forces combat while a pursuer remains. Player/PK escape legs and party raid holds retain their separate behavior.
- Bot status exposes the retreat threat name, initial resource ratios/reason, last assessment and episode completion reason under `movement.retreat`, without requiring developer diagnostics.
- Ordinary static monsters and ordinary group minions have a spawn leash and physical return/reset owned by `Npc/NpcReturnHome.js`; see [world/combat](world-combat.md). No damage-inactivity timeout is used.

## Journey planning catalogue

The [cached physical-travel P1 contract](../data/Bots/TRAVEL_CATALOG.md) and `data/Bots/travel-waypoints.json` freeze future coverage/interfaces only. They are not loaded by this runtime; cached trunks, component proofs and chunked execution are not implemented by that P1 work. The current behavior below remains authoritative.

`Bot/Travel/TravelRoutes.js` retains the existing cheapest-fare `route`/`between` and hop-only `teleportPoints` APIs. Its additive `exitRoutes(townKey)` returns cached, immutable city-prefix-plus-native-exit routes, including competing offers to the same landing. Each step has the source city/NPC, destination ID/label, native fare and authored XYZ. Only mapped city gatekeepers supply edges; field landings do not invent reverse services. Routes are a bounded candidate family, not globally fastest paths.

`Bot/Travel/JourneyPlanner.js` has no live-world or gameplay effects. Construct one shared planner per process **after** service data is loaded with `JourneyPlanner.create(TownServiceCatalog.rows(TownServiceCatalog.ROLES.GATEKEEPER))`; use authored rows, not the catalogue's live-target resolver. The planner precomputes source-spawn bindings, inter-hop walking endpoints and the minimum wallet needed for each hop list. `JourneyExecutor.js` consumes this planner for independent `VassalOrders` gathering, return and service journeys. Local NPC staging/contact and combat/follow/loot movement do not create journeys.

The returned `plan(request, measureWalk)` method resolves asynchronously:

- Required: finite XYZ `from`/`to`, positive movement `speed` in units/second, and current nonnegative `adena`. Optional: `karma` (default zero), held `scrollCount` (zero), `remainingFare` (uncapped), `arrival: { xy, z }` (96/128 units), and `allowedModes` (walk/gatekeeper/recall). `walk` controls the direct candidate; every transport itinerary still includes local approaches and a final walk.
- The caller owns goal identity, paid fare, remaining-cap calculation and bounded exclusions across replans. Refreshing the wallet or itinerary must not replenish the original goal cap. Planner inputs are not mutated, and invalid numeric inputs throw rather than manufacture coordinates/funds.
- `exclusions` accepts arrays or sets: `entries` excludes first-access source keys; `sources` excludes a spawn at any hop; `edges` excludes native `npcId:destinationId` offers; `exits` excludes final landing-to-goal access by `x:y:z`. Source keys are `npcId:x:y:z` from the selected gatekeeper leg. Boolean `directWalk`/`recall` exclude those candidates. An exit exclusion does not prohibit using that landing as an intermediate transfer; an entry exclusion does not prohibit later contact with that spawn. Exclusion expiry/retry and diagnostic ownership belong to the executor below.
- Candidates include direct walking, access to at most three nearest nonexcluded city sources, and an available held Scroll of Escape followed by walking or access in its regional town. The executor excludes automatic recall while `TownTransitPolicy.townAt` recognizes the actor's current town and rechecks this before spending a scroll; town/service proximity is not a reason to recall. Player-controlled native scroll use is unchanged. Karma disables transport. Positive-price hops require at least 50,000 Adena **before each debit**, sufficient fare funds and the remaining total cap; a paid hop may leave less than 50,000, but another paid hop then cannot follow. Free hops and a held recall scroll do not require that threshold.
- `await planner.plan(request, measureWalk)` requires an injected asynchronous walking-cost resolver. Executable candidates use complete geodata-validated path lengths/current speed for every source/inter-hop/final walk, plus a 20-second recall cast, one-second native teleport publication and estimated 1,150 ms gatekeeper dwell. These are traversable-path estimates, not globally shortest-path guarantees. Straight-line distance minus arrival tolerance is only a lower bound for ordering/pruning candidates and the existing three-entry shortlist. Probe the direct walk first, then promising alternatives; once a verified route exists, stop after six candidate probes or when lower bounds leave the fastest route's 20% window. If none is verified, continue seeking a fallback through the same bounded worker budget. Shared legs, including unavailable/deferred results, are measured once per planning pass.
- Paid candidates must save at least 30 seconds and 20% versus the measured nonexcluded direct walk. If that search was deferred, its geometric lower bound may only prove savings conservatively; it never becomes an executable route/ETA. A completed search without a route does not suppress connected transport alternatives. Within 20% of the fastest verified eligible ETA, selection prefers lower fare, then fewer hops, then a stable key.
- Success is `{ status: 'planned', key, mode, fee, hops, etaMs, legs }`, **not arrival**. Only this selected itinerary materializes `recall`, `gatekeeper` and final `walk` legs. A gatekeeper leg owns its approach as well as payment/teleport; the executor must not also create a duplicate walking leg to that NPC. Walk arrival tolerances do not replace duty polygon/service validation.
- Recall legs carry item `736`, a `landingHint` and `replanOnArrival: true`. Native `TownRespawn.restartCoords(actor)` must resolve the real recall destination; subsequent routing uses actual published arrival with the same goal spending/exclusions. Never dispatch the hint or final duty goal as a synthetic recall. Gatekeeper expected fare/XYZ likewise do not replace live native offer/contact/payment checks.
- With no eligible candidate, the result is `{ status: 'blocked', reason: 'no_permitted_route', legs: [] }`. This is a policy/exclusion/bounded-candidate result, not proof that the duty destination is globally unreachable. Unresolved resource/data probes without a verified alternative resolve as `{ status: 'waiting', reason, legs: [] }`. The planner delegates path costs through its resolver; it owns no workers, actions, timers or database operations.

### Native transport and session-local execution

`Bot/Travel/JourneyExecutor.js` exports `ensure(session, request)`, `tick(session)`, `suspend(session, reason)`, `cancel(session, reason)` and `rejectFinalAccess(session)`. Independent `VassalOrders` drive it through existing BotAI ticks; the player bypass shares the native gatekeeper action, not vassal fare policy. See [native NPC service validation](content.md#quest-and-npc-ui-flow).

- `ensure` accepts a nonempty stable `key`, destination `to`, required boolean-returning `isCurrent()` owner fence, optional `maxFare`, `allowedModes` and XY/Z `arrival` tolerances. The key must identify the owner/order revision and destination. Repeated calls retain the first fence/policy and continue the same goal; changing XYZ requires a genuinely new key. A lower cap may tighten the same goal; repeated requests cannot raise it. The fence must cover the caller's real authority, including authorized clan-loss return without requiring the former clan's continued eligibility.
- `session.journey` retains confirmed `paidFare`, the original/tightened cap, last payment/recall receipt and bounded exclusions independently of the replaceable itinerary/generation. Replanning after combat, wallet/eligibility changes or external relocation never restores spent fare or clears exclusions. Paid native hops are not refunded. Unknown payment outcomes are exposed as `paymentUncertain` and block this goal instead of inventing a zero-cost retry.
- Results report `moving`, `waiting`, `arrived`, `blocked` or `cancelled`, with reason/scope, leg index/type, mode, estimated outstanding `plannedFare`, confirmed `paidFare`, remaining cap and retry time. `arrived` checks only the supplied XYZ tolerances; the duty still validates its own polygon/height/service conditions. `BotStatus` projects a compact `movement.journey` summary; the observer inspector/profile displays its destination, state/reason, route/leg, current keeper/destination, hop position and paid/outstanding planned fare, without developer diagnostics.
- Each gatekeeper leg resolves its authored source through `NpcObjectIndex`, binds the actual live object, uses `TownNpcApproach.planOpen`, waits for readiness and `TownTransitPolicy.interact`, then calls `World/GatekeeperService.js`. The leg is latched before inventory mutation and revalidates its owner, contact, native offer, remaining cap and 50,000 pre-debit threshold. Only that hop is paid. The shared service is not given the duty goal as an invented teleport destination.
- Contact slots/queue tickets and local navigation are released on suspension, cancellation, failure, accepted departure and completion. The module does not stop unrelated replacement movement when its recorded movement generation no longer owns it. Callers must explicitly suspend/cancel before transferring local movement ownership; a retained module is not automatic lifecycle wiring. Accepted native teleports continue physically, but stale owner/generation callbacks cannot resume an old task or launch another hop.
- Advancement requires the matching native physical-arrival callback, actor and teleport sequence. A superseding teleport retires the old wait and replans from actual arrival, retaining costs/exclusions. A cleared pending flag, proximity, or 15-second unconfirmed arrival is not success: the wait remains latched/blocked without a second charge. Callbacks update state only; the owner/scheduler drives the next action through a later `tick`.
- Navigation submits only the current local target through `CompanionNavigationRecovery.move` with no live-target resolver scan. New leg/target attempts clear stale diagnostics. Worker pending/backoff reports `waiting`, not physical walking. Capacity/timeout/preemption defer through existing retry delays; repeated `PATH_BUDGET` remains `resource_limited`, never a terrain or gathering-point rejection. Completed no-progress navigation has bounded retries as well.
- Failed first access excludes that entry; failed inter-hop access excludes its incoming native edge rather than every contact with the next NPC. Missing/replaced NPCs exclude the source, changed/refused offers exclude the edge, and failed final walking excludes only that direct/landing-to-goal access. Up to 64 scoped exclusions survive replans with 60-second backoff expiry; replanning itself uses the existing one-second navigation retry interval, not a new timer/pool. A limit is a policy block, not permission to evict failures and rebuy a loop. `final_access_exhausted` is returned only for exhausted eligible final-navigation alternatives without outstanding transport/resource causes; it is still not a global reachability proof.
- `BotTownTravel.beginRegionalRecall` is a separate ordinary-scroll primitive; legacy `request`, `requestMeeting` and watchdog `recover` are unchanged. It spends held item 736 once at cast start, uses the native skill-2013 cast, resolves `TownRespawn.restartCoords(actor)` once, and passes those concrete XYZ to native `TeleportTo`. Movement, owner/actor loss, combat, changed karma, trade, cast interruption or loss of native eligibility cancels the cast without refund/re-debit. The helper returns a cancellable/validatable handle and reports spent/dispatch/cancel/physical-arrival events. Executor continuation replans after real arrival and does not recall again from the same fresh landing. Skill 2099 is not a journey edge.
- `JourneyPathCosts.js` shares the existing pathfinding worker pool at lower priority than movement, under the existing low-priority navigation work budget (80 ms accounting window per second, up to 150 ms per dispatched search). Probes return only lengths, use weighted A* (1.25, 120,000 nodes) with opt-in bounded-cost smoothing, and validate each returned segment against layers/NSWE and loaded geodata regions. No straight-line fallback is accepted without terrain validation. A 512-entry exact XYZ/tolerance/navigation-revision cache retains successful lengths for two minutes and completed no-route results for ten seconds; concurrent identical requests coalesce. Work/queue/node limits and missing geodata remain retryable unknowns, never cached as unreachable terrain.
- Planning is asynchronous and exposes `route_estimate_pending`, `route_estimate_deferred` or `geodata_missing` resource waits. It pauses duty stall clocks and commits an itinerary only through a later owner tick. Goal/generation/actor, actual origin and navigation-revision checks reject stale results; suspension cancels unshared probes without clearing confirmed fares/exclusions. No per-bot whole-world scan, new persistence ledger, background poller or worker pool is introduced. Native debit plus position persistence remains non-atomic across crashes.

`VassalOrders` pins the existing selected gathering point and validates polygon/height arrival after the final walk. Town work journeys to Gludio before handing movement to the existing supply/warehouse approach; final Castellan contact remains local. Order/party/death invalidation cancels old continuations. Actor and clan-eligibility fences also cover authorized clan-loss return without requiring continued membership in the old clan. Defense, corpse processing, trade, recovery, inventory operations and loot pickup suspend journey-owned movement/contact; an ordinary journey recall is validated before rest/buff work can take its cast. BotAI stop suspends the journey and cancels its uncommitted recall, retaining goal costs if the session resumes.

The gathering walk's 30-second clock observes only an active final walk. `rejectFinalAccess` rejects that one direct/landing access through the executor's existing exclusions; only `blocked` with `scope=final_access` permits the duty's point cooldown/reselection. Transport, resource and policy blocks do not reject the point. The independent five-minute watchdog counts observed active gather-duty idle and physical town/service work, not merely active walking. No-target hunting, an unsuitable assignment level and waiting/retrying without an eligible gathering destination pause accounting instead of consuming recovery attempts; the destination wait also clears the elapsed physical-stall clock. Worker pending/backoff/resource blocks, NPC queues/dwell, pending teleport/recall and unresolved-payment holds pause accounting, as do existing combat/rest/trade/operation exclusions; replans do not renew its recovery allowance. See [farming stall recovery](vassals.md#farming-stall-recovery).

Journeys remain session-local: normal restart restores duty/inventory/location and builds new routes, never replays old callbacks or credits downtime. Gameplay acceptance for paid/multi-hop travel, player bypass, physical arrival/supersession, interruption, contact-slot contention and worker backoff remains separate from syntax/source verification; this integration has not established runtime acceptance.

## Retained cold worker contract

Read these only when maintaining that architecture; they are not current vassal execution instructions:

1. `Population/ColdSimulationCoordinator.js` starts the worker only when the resolver is enabled and provides bounded snapshots.
2. `ColdSimulationWorker.js` excludes live World, BotManager, network and Database dependencies; `ColdSimulationKernel.js` schedules bounded snapshot work.
3. Worker proposals return through `ColdCommitQueue`; main-process database commits enforce lease/revision ownership before acknowledgement.
4. `HotActivation.js` fences worker work before handoff. `Cooldown.js` saves native state before explicit return to cold ownership.
5. `HotPartyLifecycle.js` owns whole-party publication/cooling. `BackgroundJobRegistry.js` coalesces intervals and prevents overlapping jobs; `BackgroundWorkGovernor.js` admits work against budgets and leases.

With `developerDiagnostics` enabled, the retained worker adds numeric matchup/spot-value cache snapshots to its existing heartbeat and `PopulationStatus`'s `workerCaches` summary. Counters accumulate for that worker's lifetime; sizes describe individual maps/pools, not all retained references or memory bytes. Matchup shared-group gauges and eviction/source-reset accounting run even without diagnostics to enforce a best-effort budget of 786432 verdict/spot entries; hit/miss and pool-clear counters remain diagnostic-only. The `m` summary appends `budgetEvictions` after `spotPoolClears`: drops caused only by this budget, not already due to the 4096-profile cap or ten-minute idle rule. The current group is protected, and identity hits do not refresh shared ordering; stopping at that group can leave entries over budget, including later groups. This is neither strict all-use LRU nor a hard heap limit. Unshared groups, identity-retained evicted maps and separately capped deduplication pools are outside this budget. `fingerprintHits`/`fingerprintMisses` count shared-fingerprint reuse for new profile arrays, excluding repeated identity hits. `fingerprintChars` sums shared-key `String.length` (UTF-16 code units, not bytes), and `optionMaps` counts their safety/level submaps. `verdictEntries` covers tracked shared maps only, while `spotStores` is an upper bound on their spot-result entries: garbage-collected weak spot keys are not subtracted. It excludes unshared or evicted maps still retained by profile arrays and is not an estimate for all caches. `uniqueSpotResults` is the deduplicated pool size. `sourceResets` excludes first NPC-source binding; `verdictPoolClears` and `spotPoolClears` count separate cap-driven pool clears. Spot-value `memoEvictions`, `incomeEvictions` and `baseEvictions` count individual cap removals. `bestHits`/`bestMisses` and `incomeHits`/`incomeMisses` count lookups in `best()` and `rankedIncome()` respectively; the summary appends the best and income hit/miss pairs after the reset count. Its `resets` counts nonempty instrumented invalidation groups, not rows or every clear hook; `best()` counts only its three cleared maps, not the untouched value memo. These observations do not establish a speedup or activate the worker for owned vassals.

Economic admission also reports fixed `cap:<category>:<field>` counters through the existing bounded `EconomyDiagnostics` aggregate when `developerDiagnostics` is enabled; detailed `economyDiagnostics` records are not required. Categories cover solo/group roots and nodes, solver branches, gear finalists/roots, producers, buy ads and quotes. The counters observe existing limits, not expanded admission: buy ads use the local `BoardRules` limit (currently 3 shop lines plus 5 buy-ad records). Checks, cut calls and dropped candidates are distinct; not every category supplies all three. Solo root/node drops remain in `provider:admission_pending`, while group admission has its own dropped totals. Branch cuts exclude inherited child failures and native-command re-evaluations. `cap:quotes:short` records a non-whole result after quote truncation, not proof that excluded offers could fill it; `cap:quote_use` exposes a second truncation of a retained source plan. These are bounded per-thread observations, not an exhaustive accounting of every planning failure or a runtime acceptance claim.

Gain-store diagnostics are separate per loaded `ColdCombatProfile` module/thread. `PopulationStatus.summary().gainStore` and `mainGains` describe the main process; `workerCaches` appends `gs` from the cold worker heartbeat; `clanGains` uses the clan planning worker's last completed plan. Worker snapshots are not live measurements while idle, and the retained clan snapshot can predate a worker restart. Missing worker samples retain the summary's zero-format fallback; they do not prove an observed empty cache. Counters are cumulative with `developerDiagnostics` enabled:

- `gainHits`/`gainMisses` count `gainFor` lookups; `limitMisses` counts computed misses not retained because an existing candidate/entry/nonzero limit prevents storage. These are not timings or counts of build requests.
- `switches`/`preparationSwitches` count replacements of already held current/preparation keys, not first bindings or every forget. `clanSwitches` is the subset of ordinary switches during the explicitly wrapped synchronous clan `gearGain` calculation, not all clan activity.
- `filledDrops` counts final-owner deletion of entries containing stored candidate gains, including zero gains. `evictions` counts owner-slot cap removals across both owner maps, not unique build entries freed. The existing `buildGains`/`ownerBuilds`/`ownerPreparations`/`candidateIndex` sizes are not memory-byte estimates.

`mainGains`, `clanGains` and `gs` use `buildGains/ownerBuilds/ownerPreparations/candidateIndex:gainHits/gainMisses/limitMisses:switches/preparationSwitches/clanSwitches/filledDrops/evictions`. Counting adds fixed scalar state per thread, not per-bot records or new world scans. The clan calculation keeps its direct path without a diagnostic callback allocation when diagnostics are disabled. Cache limits, retention/refcounts and gear decisions are unchanged; these observations do not establish a speedup.

The competition-frame size predictor reserves the same optional numeric cache shape with diagnostics on or off, including the four best/income lookup counters and twelve gain-store size/counter fields, using its existing conservative numeric padding. The 256-KiB IPC limit is unchanged, but the larger reserved envelope can reduce a limit-bound legacy event batch in both modes. Snapshot collection is constant-size work; diagnostic counting is guarded, not a promise of zero overhead when disabled.

The population scheduler timer in the retained coordinator is not evidence of a main-thread cold simulation loop. The [resource competition document](../src/GameServer/Bot/Population/COLD_COMPETITION.md) contains broader historical contracts and must be read with this activation boundary.

## Pathfinding remains a separate worker boundary

`src/GameServer/Actor/Generics/MoveTo.js` selects asynchronous native pathfinding for vassals and excludes their legacy low-detail warp. Results are checked against current actor, route generation, target and location before movement.

`src/GameServer/Geodata/PathfindingWorkerPool.js` provides bounded queues, cancellation and deadlines with lazy worker creation. NPC movement also uses it. Disabling the **cold simulation worker** does not disable these pathfinding workers.

## Optional MCP manual authority

[Bot MCP control](bot-mcp.md) defaults to read-only attachment. Explicit manual acquisition refuses native busy/publication holds, stops autonomous scheduling, invalidates vassal/journey and queued/async continuations, and uses an explicit `bot-mcp` action owner rather than impersonating player auto-fight. BotAI activation/ticks, provider entry and autonomous queued pickup are gated until handoff settles. World damage/effects/pet lifetime still run; accepted native actions retain their own completion correlation. Deferred SP training reconciles before current-duty resumption. Separate heartbeat and idle deadlines bound authority; a read or replay is not renewal. A native stop vetoes resumption, and an initially inactive AI is not started by observation/release. The shared active-handoff sweep is bounded to 12 states, not a timer or world scan per bot. P3 native publishers allocate structured events only for observed registrations; attachments share one bounded journal, which survives return to AI and is freed with the last subscriber. State/decision/path sampling runs on existing AI/publication/read paths, not a new population poller. Local/detail pages charge native cell/candidate work before projection; only active waiters use one shared timer. P4 joins selected service adapters to the same foreground: native debit/award/commit/publication tails survive revoke/disconnect, while new admission is fenced. Unknown settlement retains the hold, not an automatic refund or AI restart. The issued-offer context is generation/NPC-bound and bounded; no new per-bot service poller is added. After return, the same observation journal can show actual native decisions; deployed resumption/service acceptance still requires a live check.
